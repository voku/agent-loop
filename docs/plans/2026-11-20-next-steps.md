## 2. Global rules (non-negotiable)

1. **Never approve anything yourself.** No `workflow approve`, `proposal-approve`, review acknowledgement or merge authority invented by an agent. When the lifecycle returns `decision_required`, show the exact subject and stop.
   - Only exception: inside a disposable experiment workspace under an approved experiment protocol, the operator (the orchestrating session acting for the human owner) approves as submitted and logs each approval.
2. **Follow agent-loop's lifecycle in agent-loop work:** `bin/agent-loop enter <task-id> --format=json` before edits, and `bin/agent-loop finish <task-id> --format=json` after. Obey each `next_action_kind` / `next_action`.
3. **Owner-first.** Change the owning package first (Recall, Map, Learning, Edit, Session), release it through its marker flow, then bump and integrate in agent-loop. Never copy owner semantics into Loop.
4. **No API keys and no credentials in prompts, env vars or scripts.** Use the account's existing GitHub integration only.
5. **Evidence, not claims.** Say "passed" only with a run you can cite: an exact-head CI run, or a command output. Report negative and null results as results.
6. **Do not edit `MEMORY.md`, Learning records, constraints or skills directly.** Use the Learning workflow (Task T3).
7. **Ponytail lens:** before adding code, a gate, a schema field or a subsystem, name the concrete failure it fixes. "We could measure it" is not a reason. Prefer a verified `NOT_USED` or "do nothing".

### Environment gotchas (observed in cloud containers)

- Composer refuses to run as root. Prefix commands with `COMPOSER_ALLOW_SUPERUSER=1`.
- GitHub zipball downloads can fail through the egress proxy (`ws_closed_mid_exchange`). Composer then falls back to full git clones and can fill the disk. For lock-only bumps, keep the lock diff minimal and let CI install.
- The disk is a fixed allowance. Hardlink large vendors (`cp -al`). `rm -rf $VAR/...` is refused by a safety check: use literal absolute paths.
- Do not write into the host's own `.claude/` configuration; it is treated as changing your own harness.
- `gh` CLI: in cloud sessions use it only for code search and use the GitHub MCP tools for everything else. T7 is the exception: it runs on a separate machine with its own `gh` login.

- **Goal:** answer "does a real host load `coding-simplicity` after an explicit extra-skills-root projection?" without building instrumentation.
- **Status:** probe **P-N1** exists only in the 2026-11-20 container.
  - Setup: workspace at baseline `5f54b84e`, lesson `481001` removed, then `bin/agent-loop init install-assets --agent=claude --extra-skills-root=<agent-skills@c9e3b296>/skills --skip-git-config`. That projects 42 skills into gitignored `.claude/skills`.

  - Before approval, P-N1 opened no skill file, and its plan contained a speculative declared-parent fallback.
- **Facts already established:**
  - Sub-agent hosts get their skill catalog from the parent session, not from the workspace. The pilot catalogs never contained the projected skill.
  - Hosts can load a skill without the Skill tool (`cat .claude/skills/...` via Bash). A file read can also be source editing, not use.

  - Recall's `recall-log.draft.json` can only record outcomes for *selected Learning guidance* (memory, constraint). Package skills are never selected, so no row can name them. `also_prescribed_by` takes only the category `skill`. Session evidence is free text or command/exit-code records.
  - **Conclusion so far:** no existing typed evidence can say "skill X was loaded".
  - **Prior art:** PR #727 (`.github/workflows/codex-skill-consumption-proof.yml`) already proves **explicit** skill consumption for Codex 0.157.0.
    - It runs provider-free: it captures real provider requests and requires the SKILL.md body marker to be absent at baseline and present after `$agent-loop-workflow`.
    - Evidence class: `host_runtime_skill_consumption`.
    - **Implicit routing, `voku/agent-skills` skills and other hosts are recorded as unclaimed** (`docs/architecture/first-party-capability-matrix.md`).
    - Implicit selection needs a real model to decide. A provider-free proof cannot show it.
- **Steps if P-N1 finished in this container:**
  1. Grade it like the pilot. Add `P-N1\t<agent-id>` to `runmap.tsv` and run `grade_pilot.py`, `oracle_h2b.py`, `fp_h2b.py`.
  2. Run `audit_transcripts.py` and record `skill_access`.
  3. Classify the outcome as **NOT_LOADED**, **LOADED_NOT_APPLIED** or **LOADED_APPLIED**. "Applied" means the design avoids speculative surface *and* the transcript links the choice to the skill.
- **Steps if the container is gone:** redo P-N1 with `prep_h2.py` + `install-assets` as above, one run, the same prompt.
- **Deliverable:** a section "Activation probe: explicit-root projection, no pointer" in `docs/dogfood/2026-11-20-learning-effect-h2-screening.md`, with:
  - the three-claims table (available / loaded / applied, each with its evidence source);
  - the smallest verified observability gap;
  - options:
    - (a) **do nothing**: record the gap and keep `DEFER`;
    - (b) **routing-only**: make the always-on bootstrap name `coding-simplicity` for coding tasks. This is a guidance change and conflicts with the matrix row `REJECT session reinjection`, so it is OWNER;
    - (c) **extend the existing #727 proof pattern**, *only* if a concrete decision needs it: add a paired implicit-routing case for one Claude or Codex host with a real model, outside Loop/Session schemas. A typed Session field (`skills_loaded`) is the last resort and would go to agent-session first.

- **Do not:** modify Loop, Session, Learning, `MEMORY.md` or the skill.
